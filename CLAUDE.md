# artol-ai — Active project context

PH floor plan generator + validator. Single-detached mid-market houses. CP-SAT solver.

## ⚠ READ FIRST — setbacks changed 2026-08-05 (front 2.0 → 3.0 m)

Lot setbacks are now **derived from occupancy class**, not hardcoded. The
project defaults to **R-2 (3.0 m front, 2.0 m side/rear)**; R-1 keeps the
stricter 4.5 m front and applies to any brief declaring it.
`core/validator.py::SETBACK_MIN_BY_OCCUPANCY` is the single source of truth and
now drives BOTH `ai/pipeline.py::_make_default_lot` and validation. It also
**clamps explicit `Brief.setbacks`** (a deliberate `0` firewall excepted), so a
brief can no longer sit below code.

**Every lot size quoted in prose in this file predates 2026-08-05 and was
derived under a 2.0 m front, so it is 1 m short of depth.** Adding 1 m of lot
depth restores the identical envelope — `(depth+1) − (front+1) − rear =
depth − front − rear` — which is why the 26 test briefs that went infeasible
were all fixed by exactly that, and renamed (`1s_2br_10x10_...` →
`1s_2br_10x11_...`), with their plans unchanged.

**→ Use the "Verified minimum lot sizes" table below, not the prose.** That
table is generated by execution against today's rules. The ~200 dimension
mentions scattered through the topology lists and "Recently completed" entries
were deliberately NOT rewritten: most are historical narrative recording what
was tested under the old rule, and editing them would turn accurate records
into false ones. Read them as history; read the table as current fact.

Detail: `SHELL_CAPPING_DESIGN.md` §1a.

### Polished render via Gemini "Nano Banana" — **evaluated, 11 calls, ~$0.44**

Full write-up: **`NANO_BANANA_RENDER_DESIGN.md` §9**. Read it before spending
another peso on this. Headlines:

- **Prompt FRAMING dominated everything.** Six versions in `ai/render_prompt.py`
  said "redraw"/"restyle" and ALL invented dimension figures. A user-written
  prompt opening *"**Convert** the provided floor plan image into a 2D
  architectural render"* got every figure right first try, having been told
  nothing about numbers. Kept verbatim at **`ai/prompts/convert_render.txt`**.
- **Counted checklists work; prohibitions do not.** "EXACTLY 5 doors" produced
  the kitchen service door that four rounds of prose could not. Counts are
  derivable from the manifest, so this generalises.
- **Marking a target IN THE IMAGE beats describing it** — the most consistent
  finding across all 11 runs: this model follows the picture, not the paragraph.
- **The same prompt is not reproducible.** Identical text + identical source
  gave a good render once and a broken one the next time (lost `BEDROOM`
  label, `MASTER BR` corrupted to `...ERR`, `3.1x3.7 m` against a real
  `5.4x3.7`). **A good render is therefore not a property of the prompt that
  produced it**, and no tuning fixes that.
- **Conclusion: use it for STYLING, supply every FACT by composite.**

**Hard user constraint, structural not configurable:** polish must NEVER run
automatically when floor plans are generated. `run.py` has no polish flag and
no import of the polish stack; `python3 polish.py --self-check` proves it and
should stay passing.

`polish.py` flags: `--brief` (required, no sweep mode), `--plain` (solver
drawing unmodified), `--prompt-file` (verbatim — nothing appended, so a
hand-written prompt stays a controlled experiment), `--raw-output` (skip the
composite), `--dry-run`, `--yes`, `--self-check`.

## Current focus (as of 2026-06-25)

**Naming convention locked:** `{storey}_{nbr}_{WxD}_{shape}_{strategy}_{bath_token}[_hall][_gr|_ld]_{carport}[_swap]`
Shapes: `sq`, `wd`, `dp`, `swd`, `sdp` | Strategies: `side_split`, `front_rear`, `l_wrap`, `z_wrap`, `split_wing` | Bath: `bath`, `bath_pwd`, `baths_cl`, `baths_ds`, `baths_mix` | Carport: `ncp`, `fcp`, `ccp`

**Carport type semantics (locked; setback numbers updated 2026-08-05):**
- `ncp` — no carport; building_void + carport setback element stripped; rectangular envelope.
- `fcp` — full carport; the carport side is at least 3 m for the entire depth; building_void stripped; rectangular envelope (narrower shell than ccp). Set `carport_side` + `carport_type: fcp` in brief.
- `ccp` — claimed carport; 3 m for first 6 m of depth, then the class minimum beyond; L-notch via building_void.

## Key project conventions

- **Ask before coding.** Discuss approach, get explicit go-ahead, then write code. See [[ask-before-coding]].
- **Every bedroom needs hallway/public access** — never via a bathroom. See [[floorplan-quality]].
- **Don't present mirror-image variants** as distinct designs.
- **Floor area bands** per [[floor-area-per-br]]: 2BR/1bath 45–65, 2BR/2bath 65–80, 3BR/2bath 80–120, 4BR/3bath 100–150 m². No locked 1BR band yet — the 7 topologies built 2026-07-16 land around 24–36 m² each, treat as a working range not a locked convention.
- **Rear-linear topology (bedrooms across rear) is infeasible** with current solver — use side-split column-stack instead. See [[rear-linear-infeasibility]].
- **1BR topologies need `private_area_floor: false`** — the solver's hard "private ≥ public" area rule assumes a multi-bedroom private wing; a single bedroom can never satisfy it against a full LDK. See [[solver-topology-overrides]].
- **Zone ratio (private/public split) is now per-topology configurable, not just on/off.** `zone_ratio_private_floor_pct` / `zone_ratio_private_target_pct` (both default 50.0/55.0, reproducing the old fixed 55/45-favoring-private behavior byte-for-byte for every topology that doesn't set them) generalize what used to be hardcoded constants in `solver.py`'s zone-ratio block. Use for a deliberately public-heavy design (target < 50 — keep floor ≤ target on that side of 50 or the hard floor contradicts the soft target and the block goes infeasible). See [[zone-ratio-configurable]].
- **Dead-strip reclaiming is ALWAYS ON and deliberately permissive — there is no `claim_dead_strips` flag any more** (removed 2026-08-06 from the dataclass, loader, 7 copy sites and 5 topology JSONs; don't go looking for a switch). Rationale: these plans are **customer-discussion documents** and a brief for the architect who draws the official version, not construction sets — an unexplained interior void reads as a mistake, while a slightly irregular room reads as "this space belongs to the living room". So the claimer favours the room that obviously owns a strip over rule-keeping: no master-supremacy check (it still holds at solve time and during snap growth, so only the LABELS can show a standard marginally larger), room-type priority is a tie-break not a gate, thickness floor 0.25 m, contact floor 0.2. **The one rule that survives is the daylight guard** — a claim is skipped if it would cut a window-requiring room off from the exterior, because that is a hard PD 1096 §808 error that makes the plan an unusable brief. Don't remove it when loosening further. Prefer this over `match_widths`/width-pinning, which ADD solver constraints and break feasibility at exactly the tight sizes you're trying to fix.
- **The anchor-trap SIGNATURE is a reason to TEST, not a diagnosis.** Nine
  topologies arriving 2026-08-12/14 all declared `left_anchored` +
  `right_anchored` + `rear_anchored` together, but the causes differed and one
  file had no problem at all: `1s_3br_wd_side_split_baths_cl_hall_gr` solves as
  authored with all three kept, and `1s_3br_wd_split_wings` was broken by
  `front_to_rear_stacks` instead — "fixing" its anchors would have removed
  constraints that were never at fault. Always bisect at an oversized envelope
  (25×25 squarish, 25×18 wide) and let the bisection name the culprit.
- **A solve is not proof the parti survived, and that decides whether a
  topology ships under its own name.** Three outcomes recurred: the parti holds
  (`side_corridor`, `wd_split_wings` — ship as authored); the parti dies but
  what remains is a good building (squarish `half_spine` → shipped as
  `front_back_split_baths_ds_hall_gr`, parent retained for redraw); or the
  result is degenerate (both `center_spine` files — deleted; the wide one gave
  a **1.2 m² ensuite**). Always dump room rects and look at the render before
  writing a brief.
- **Read a topology's `notes` sceptically — six files carried a WRONG
  diagnosis.** They claimed "a reproducible, environment-specific solver issue
  affecting the spine/hall parti family broadly, not a defect this file
  introduces", and cited each other as corroboration. Every one was the
  over-constrained-anchors trap in the file itself. A `STATUS:` block asserting
  the environment is at fault should be re-tested, not believed.
- **A `lot_adjustment_profiles` entry can be DEAD CODE.** Both squarish
  `half_spine` and `side_corridor` shipped profiles whose
  `buildable_area_lt_sqm` threshold sits BELOW any lot the topology can
  actually solve, so they never fire. Check the threshold against the
  topology's real feasible range before assuming a profile is doing work —
  and note that forcing one on can make the solve infeasible instead.
- **New 3BR topologies: check for the over-constrained-anchors trap before trusting feasibility.** Declaring `left_anchored`+`right_anchored`+`rear_anchored` together routinely fights a topology's own `front_to_rear_stacks`/adjacency graph and produces infeasibility at EVERY lot size (proven twice, 2026-07-19). Test at an oversized envelope first; if infeasible, bisect anchor lists before suspecting adjacencies. See [[solver-topology-overrides]].
- **Authoring a 2-storey topology:** follow [[multistorey-topology-authoring]] step by step (storey tags, the three stair adjacency kinds, the always-on stair-run override, `zone_balance_rooms` for public-heavy ground floors, hall/hall-less as siblings not a conditional room). Architecture background in `MULTISTOREY_V2_DESIGN.md`.
- **Prefer a fixed door over `door_host_group` when the desired host scores worse than the alternative** — Pass 1a's auto-scorer will silently flip a group's default to whichever host wins on circulation-overlap, so a group can't reliably hold a deliberately-suboptimal-scoring choice. See [[br1-topology-catalog]] (door-host-group finding on `wd_side_split_bath_gr`).
- **Never hold per-layout state in a module global — and if you must, clear it on the way out.** A probe cached in `architectural_plan._OUTSIDE_PROBE` leaked between briefs: output became deterministic-but-CONTEXT-DEPENDENT, so a brief run alone differed from the same brief run in the full suite, and a refreshed baseline still showed drift. It was justified when added as "safe because the pipeline is sequential" — that is exactly backwards; sequential execution is what lets one brief's state reach the next. Symptom to watch for: `--brief=X` and a full `--test` run producing different output for X. Related trap: anything built from `layout.rooms` on a MULTI-STOREY layout sees BOTH storeys unless you scope it to one.
- **Measure any room-size change across the FULL test suite, never a sample, and compare SVGs by element multiset.** A 1-in-3 sample of a kitchen preferred-low change reported "0 rooms shrank"; the full suite showed 6 shrank, one to 3.41 m². And these SVGs are emitted as a single line, so a line-diff can't see reordering — up to 13 files reshuffle between runs with byte-identical inputs, which inflates any byte-based drift count. See `SIZING_OBJECTIVE_INVESTIGATION.md` and [[preferred-low-cliff]].
- **Don't raise a `preferred_area_sqm` low value expecting rooms to grow.** The objective's preferred-low bonus is an all-or-nothing step worth `BIG*w`, so raising a target that a shell can't reach makes the room *lose* its incentive and get stripped toward the hard minimum to fund some other room's step. Proven twice (bedroom → 6 m² legal floor; kitchen 6.12 → 3.41 on a roomy 16×12). Fix the objective first — a graded-credit prototype exists, default-off. See [[preferred-low-cliff]].
- **A `_gr`/`_ld` pair is ONE topology with two implementations, not two topologies.** Link them with `fallback_below_buildable_sqm` on the `_ld` pointing at the `_gr`; the runner then routes by buildable area before attempting a solve (design intent, not an infeasibility fallback), and `build_catalog.py` collapses them into a single catalog entry with Default/Fallback tabs. Grouping keys on that fallback LINK, not on the name suffix, so the same idiom covers hall/hall-less. **Always evaluate the gate on the RAW envelope**, never the shell-capped one. Do NOT try to merge the two into one topology file — the programs differ by an actual room split (`great_room` vs `living_room`+`dining_room`, changing adjacencies, stacks and `entry_point`), and the project already settled this for hall/hall-less: siblings, not conditional rooms.
- **After changing setbacks or room sizes, audit for SILENT TOPOLOGY SUBSTITUTION, not just infeasibility.** A brief whose topology becomes infeasible may quietly fall back to its sibling and still report PASS — so the fixture no longer tests what it claims. Two briefs did exactly this after the front-setback change and were only caught by comparing the solved `topo.id` against the declared one. `run.py --test` will not tell you.
- **Adding a topology to the catalog changes what the AI path teaches Claude — no prompt edit needed.** Since 2026-08-05 the few-shot exemplars in `ai/prompt.py` are selected per brief from `topologies/` via `select_exemplars`, so a new topology becomes an exemplar for briefs matching its bedroom_count + shell the moment its file lands, and a *deleted* one silently stops being one. Corollary: a topology's `label` is now prompt input, not just catalog prose — it's what Claude reads as that exemplar's brief when there's no hand-written text for the file. Write labels accordingly. See [[ai-exemplar-selection]].
- **A window can sit on an L-shaped room's ALCOVE, not just its main rect.** `_place_windows` iterates `room.cells`, and `Window.cell_index` (0 = rect, 1 = alcove) tells the renderer which cell `position_m` is measured along. This matters because a dead-strip claim can extend a previously-interior room out to the envelope: before 2026-08-06 the validator saw the new exterior wall and demanded a window while the placer only looked at `rect` and placed none, giving a hard `window area 0.00` failure.
- **The building footprint is the union of ROOM cells, not the envelope rectangle, and there is exactly ONE definition of "exterior wall": `core/model.py::make_outside_probe`.** A wall is exterior when the space beyond it REACHES the outside (flood-fill), not merely when it sits on the envelope edge. `Layout.footprint_area` has always summed room areas, so the arithmetic always agreed; before 2026-08-06 `render.py` and `architectural_plan.py` each had their own answer and disagreed — a wall exterior only because it faced an unclaimed perimeter strip was drawn heavy but got no window and could host no door. Both now consume the shared probe, which gates window placement, the front door, the kitchen service door and perpendicular-wall detection. Consequence: outlines are legitimately **non-rectangular** — stepped, with the setback wider on that side. A gap fully ENCLOSED by rooms is a courtyard and stays interior. Don't "fix" a stepped outline by assuming the envelope should be filled.
- **Log every topology/brief/shared-render-code change to `TOPOLOGY_CHANGES.md`** (repo root) as it happens — new/modified topology, new/modified test brief, or an edit to `solver/*.py`/`core/render.py`/`core/model.py`/`ai/brief.py`/`run.py`. `artol-topologies/` (the published HTML catalog) is a build artifact regenerated from a snapshot; the tracker is what lets a single regen pass fold in everything since the last build instead of re-deriving a diff from git history. Shared-code entries have catalog-wide reach — flag them as "regen the whole site," not "these N topologies."
